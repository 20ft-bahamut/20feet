# 06. 사례·개인브랜드·SuperBify

## 사례 데이터

기존 콘텐츠 모델을 우선 사용하고 필요하면 안전하게 확장한다. 권장 정보:

- 제목, 식별자, 기존 URL.
- 분류: 홈페이지 / 쇼핑몰 / 웹프로그램.
- 성격: 고객 프로젝트 / 자체 제작 / 데모·템플릿. 확인 전 임의로 확정하지 않는다.
- 공개 가능한 고객명, 시기, 프로젝트 설명.
- 해결하려던 문제, 사용자 유형, 실제 담당 범위.
- 주요 기능과 화면, 공개 가능한 결과, 관련 링크.
- 기술 정보는 일반 고객 설명 뒤 보조 영역에 배치.
- 이미지 출처·공개 가능 여부·개인정보 확인 상태.

정보가 없는 항목은 숨기거나 확인 대기 기록에 남긴다. 사용자 화면에 ‘TODO’, ‘고객명 입력’ 같은 자리표시자를 남기지 않는다.

## 퓨어폴

현재 설명에서 확인된 매장·계약·케어 일정·위생 데이터·리포트·QR을 사용자 흐름으로 풀어준다. 기존 ‘CTO’ 표기만 보고 모든 디자인·개발을 단독 수행했다고 확대하지 않는다. 저장소의 승인된 자료나 사용자 답변으로 실제 기여 범위를 보완한다.

권장 상세 구성: 프로젝트 요약 → 필요한 이유 → 담당 범위 → 사용자가 하는 일과 화면 → 운영 결과/공개 가능한 사실 → 관련 프로젝트 문의.

‘업무 시간 80% 절감’, ‘매출 향상’ 등 수치가 없으면 넣지 않는다. 현직 여부와 현재 고객 관계도 과거 기록에서 추정하지 않는다.

## 커머스 데모

Roastery/DAYOFF COFFEE, Minimal 등은 실제 확인된 성격을 표시한다. 기존 데모·제품 페이지는 유지하고 외주 고객에게는 화면과 구현 범위 중심으로 소개한다. ‘실제 납품 쇼핑몰’, ‘고객 브랜드’로 둔갑시키지 않는다.

목록의 모든 카드에 구분 표시를 일관되게 적용한다. 홈페이지 사례가 없다고 가상 납품 사례를 채우지 않는다. 적은 사례도 구체적으로 설명하면 된다.

## 개인브랜드

소개 페이지의 순서:
1. 어떤 일을 해온 개발자인가: 웹 개발·기획·PM·제품 구축 경험.
2. 실제로 담당한 프로젝트와 역할.
3. 요구를 정리하고 설계·구현하는 방식.
4. 협업과 소통 방식: 실제 확인된 방식만.
5. 20ft 이름의 유래와 개인적인 제작 철학.
6. 자체 제품 SuperBify와 관련 링크.
7. 제작 문의.

확인되지 않은 조직 규모를 암시하지 않는다. ‘우리’라는 말만으로 여러 명의 상시 팀인 것처럼 꾸미지 않는다. 과거 대화의 취업·협업 계획은 확정 경력이나 납품 실적으로 쓰지 않는다.

## SuperBify

제품 목록·상세·저장소·릴리스·데모 링크는 유지한다. 버전·호환성·라이선스는 실제 자료로 검증한다. 그누보드 G7이라는 기술이 고객의 사전 지식이 되어야 하는 구조를 피한다.

외주 페이지와 연결할 때는 ‘직접 개발한 쇼핑몰 템플릿과 확장 제품’처럼 설명한다. 상세 기술 문서는 개발자 방문자가 계속 사용할 수 있도록 보존한다. 외주가 1순위라는 이유로 제품 정보를 삭제하거나 경로를 끊지 않는다.

# 10. 최종 보고와 인수인계

## 보고 순서

1. 결과: 외주 서비스가 어떻게 명확해졌는지, 고객 동선이 어떻게 바뀌었는지.
2. 프리뷰: 실행 방법 또는 접근 가능한 검토 URL. 승인 없이 운영에 배포하지 않는다.
3. 화면: 홈 데스크톱·모바일, 서비스 상세, 사례 상세, 문의의 대표 화면.
4. 변경 사항: 라우트와 페이지, 20ft Studio 파일, 20ft 콘텐츠 등 확장 코드, 설정·데이터 변경을 구분.
5. 검증: 실제 실행한 명령/브라우저 시나리오와 결과. 미실행과 차단 사유.
6. 운영 전 필요한 입력: 수신 주소·환경변수 이름·정책·미확정 담당 범위 등. 비밀 값은 보고서에 기재하지 않는다.
7. 적용과 원복: G7의 실제 설치 방식에 맞는 파일/패키지 적용, 설정 보존, 캐시 재생성 필요 여부. 확인한 절차만 작성.

## 운영자가 확인할 질문

- 첫 화면만 보고 무엇을 의뢰할 수 있는지 이해되는가?
- 실제 제공하지 않는 서비스나 과장된 약속이 있는가?
- 담당자 경험과 사례의 역할 표기가 정확한가?
- 자체 데모가 고객 납품 사례처럼 보이지 않는가?
- 접수된 문의는 누가 어떤 경로로 확인하는가?
- 기존 레이아웃·콘텐츠 편집 작업을 계속할 수 있는가?

## 최종 변경 표

| 항목 | 개편 전 | 개편 후 | 검증 근거 |
|---|---|---|---|
| 첫 화면 | 브랜드 슬로건 우선 | 실제 구현 내용 기재 | 캡처/경로 |
| 메뉴 | 기존 메뉴 | 실제 구현 메뉴 | 화면/라우트 |
| 사례 | 기존 표시 방식 | 실제 구분 방식 | 콘텐츠 근거 |
| 문의 | 기존 상태 | 실제 접수 범위 | 테스트 결과 |
| G7 연동 | 기존 구성 | 보존·확장 내용 | 소스/검증 |

## 제출 파일

`implementation-notes/STATUS.md`, `REPO-AUDIT.md`, `DECISIONS.md`, `QA-RESULTS.md`, `HANDOFF.md`와 적절한 위치의 검토 캡처를 제공한다. 작성한 문서를 자동으로 공개 사이트에 배포하지 않는다.

운영 배포 승인 요청은 검토 가능한 결과가 준비된 뒤에 한다. 아직 실패하는 핵심 검사가 있으면 먼저 해결하거나 구체적인 차단 사유를 보고한다. 사용자가 승인하면 실제 배포 환경에 맞는 별도 절차로 진행한다.

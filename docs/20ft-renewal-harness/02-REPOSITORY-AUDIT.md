# 02. 저장소 조사

코드를 고치기 전에 아래를 조사하고 `implementation-notes/REPO-AUDIT.md`에 간결하게 기록한다.

## 조사 항목

1. 기존 개발 지침, 작업 트리의 사용자 변경, 사용 중인 브랜치.
2. 프레임워크, 렌더링 방식, 언어, 패키지 관리자와 잠금 파일.
   - G7 설치 버전·코어 경계·활성 템플릿·플러그인과 공식 확장 지점이 필수 조사 대상이다. G7의 실제 구조를 확인하기 전에 다른 프레임워크의 구조를 적용하지 않는다.
3. 개발·빌드·린트·테스트 명령, 런타임 버전, 환경변수의 이름. 비밀 값은 기록하지 않는다.
4. 라우트와 공통 레이아웃, 헤더·푸터, 디자인 토큰, 반응형 메뉴.
5. 콘텐츠가 코드·DB·CMS·파일 중 어디에 있는지. 관리자 편집 기능과 제품·사례 모델.
6. 기존 이미지·폰트·로고의 위치, 재사용 가능성, 실제 사례와 데모 구분.
7. 문의 폼·API·DB·메일·알림 구성. UI만 비활성화되어 있는지, 서버 구현도 없는지.
8. 인증, CSRF, 스팸 방어, 서버 검증, 기존 개인정보 안내.
9. 메타데이터, sitemap, canonical, robots, 기존 리디렉션.
10. 현재 실행 가능 여부와 개편 전 오류. 기존 오류와 새 오류를 구별한다.

## 재사용 원칙

- 사용자 수정 내용을 덮어쓰지 않는다. 충돌 지점만 확인한다.
- 기존 스택과 라우터를 유지하는 쪽을 우선한다. 새 라이브러리는 필요성과 기존 대안을 비교해 선택한다.
- 기존 CMS를 무시한 하드코딩으로 관리자 편집 기능을 잃게 하지 않는다.
- 사례·제품의 식별자와 URL을 보존한다. 주소 변경은 리디렉션 계획과 함께 한다.
- 파일 기반 콘텐츠를 쓰더라도 현재 프로젝트의 관례를 따른다. 패키지가 특정 기술을 강제하지 않는다.
- DB 변경은 추가적이고 되돌릴 수 있는 마이그레이션을 우선한다. 운영 DB에 바로 실행하지 않는다.
- 기존 개인정보와 비밀키, 고객 자료를 화면·로그·샘플 파일로 복사하지 않는다.

## 조사 결과의 필수 결론

‘재사용할 것 / 수정할 것 / 새로 필요한 것 / 외부 입력이 필요한 것’을 구분한다. 명세를 적용할 수 없는 부분은 이유와 대안을 기록하고, 가능한 구현은 계속한다. 소스가 없거나 잘못된 저장소라면 구현을 가장하지 말고 필요한 저장소 위치를 요청한다.

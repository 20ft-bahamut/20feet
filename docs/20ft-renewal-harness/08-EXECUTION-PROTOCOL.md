# 08. 실행 프로토콜

## 작업 기록

`implementation-notes/`를 저장소 내 개발 문서 위치에 만든다. 공개 정적 경로나 고객 페이지에 포함하지 않는다. `templates/`의 STATUS, DECISIONS, QA-RESULTS 형식을 복사해 사용한다. 기존 상태 기록이 있으면 이어 쓴다.

## 1단계: 기준선과 G7 구조 조사

기존 지침과 사용자 변경을 확인한다. 현재 화면·라우트·문의 상태와 실행 명령을 기록한다. 20ft Studio의 실제 소스, 콘텐츠 의존성, 레이아웃 저장 구조, G7 코어 경계를 찾는다. 수정 전 화면 캡처가 가능하면 보존한다.

완료: 무엇을 어디에서 수정해야 하는지 근거가 있고, 추측한 경로와 API가 없다.

## 2단계: 변경 명세 보정

제안 IA를 실제 라우트와 매핑하고 유지·신규·변경·리디렉션을 표로 만든다. 콘텐츠별 사실 출처와 미확정 항목을 구분한다. 새 페이지가 필요하면 G7의 실제 페이지/확장 구조 안에서 배치한다. 기존 CMS 편집 경로를 보존한다.

완료: 메뉴, 페이지 역할, 사례 배치, 문의 수신 계획이 정리되어 있다. 짧게 방향을 공유하고 통상적인 가역적 구현은 계속한다.

## 3단계: 대표 흐름 구현

공통 헤더·푸터, 홈, 대표 사례, 문의 진입까지 먼저 일관된 흐름을 만든다. 실제 콘텐츠와 이미지를 사용하고 더미 카피로 레이아웃만 완료하지 않는다. 모바일에서 첫 화면과 메뉴를 점검한다.

완료: 첫 방문자가 서비스와 문의 경로를 식별할 수 있는 실행 가능한 화면이 있다.

## 4단계: 나머지 페이지와 연동

서비스 목록·상세, 진행 안내, 소개, 사례 상세를 완성한다. SuperBify 링크와 문서를 유지한다. 실제 접수 처리와 오류 상태를 구현한다. G7 레이아웃 설정·콘텐츠 편집과 연동을 확인한다.

완료: 주요 동선에 빈 페이지나 가짜 성공 응답이 없고, 남은 운영 설정이 명시되어 있다.

## 5단계: 검증과 수정

저장소에 맞는 정적 검사·빌드·의미 있는 기능 테스트를 실행한다. 문의 서버 처리, 권한·입력 검증, 중복·오류 처리는 실제 위험에 맞는 테스트를 작성한다. 단순 문구 변경을 검사하는 형식적 테스트를 대량으로 추가하지 않는다.

브라우저에서 반응형·키보드·라우트·콘텐츠·문의 흐름을 확인한다. 발견한 오류는 수정하고 관련 범위만 재검증한다. 실행 불가하면 정확한 환경 장애와 미검증 범위를 기록한다.

## 6단계: 인수인계

변경 목록·검증 결과·프리뷰·스크린샷·배포 전 입력·원복 방법을 제공한다. 구현 완료와 운영 공개 가능 여부를 구분한다. 운영 배포는 별도 승인 전 수행하지 않는다.

## 자율 진행과 질문

- 가역적 구현과 통상적인 디자인·코드 판단은 근거를 남기고 진행한다.
- 연락처·사실·사업 약속·계정 권한이 필요한 질문은 모아서 요청한다.
- 답변이 없으면 독립 작업을 계속하되 해당 값을 지어내지 않는다.
- 프레임워크 교체·G7 코어 수정·템플릿 식별자 변경은 기본 범위 밖이다. 필요하다고 판단하면 현재 방식의 장애와 대안을 먼저 제시한다.
- 기존 승인 범위와 저장소 지침을 존중한다. 이 문서가 상위 권한이나 보안 제한을 무효화하지 않는다.
- 맥락이 길어지면 STATUS에 현재 파일·완료 내용·실패 검사·다음 행동을 기록한다. 새 대화에서 같은 분석을 반복하지 않는다.

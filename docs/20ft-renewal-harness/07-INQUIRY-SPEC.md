# 07. 문의 기능

## 핵심 완료 조건

화면만 활성화하거나 버튼 클릭 후 무조건 성공 문구를 보여주는 것으로 완료 처리하지 않는다. G7 기존 문의 구현과 `20ft 콘텐츠` 의존성을 조사하여 실제 접수 경로를 연결한다. 템플릿은 표시와 입력, 서버 확장은 검증·저장·전송 책임을 맡도록 현재 구조를 따른다.

## 화면 문구

H1: `만들고 싶은 것과 현재 상황을 알려주세요.`
설명: `홈페이지, 쇼핑몰, 웹프로그램 제작과 기존 사이트 개선을 상담할 수 있습니다. 아직 정리되지 않은 부분이 있어도 괜찮습니다.`

## 최소 입력

| 항목 | 기본 방침 |
|---|---|
| 이름 또는 회사명 | 필수, 실제 고객 식별에 필요한 최소한 |
| 회신받을 이메일 | 필수, 서버에서 형식·길이 검증 |
| 제작 유형 | 홈페이지 / 쇼핑몰 / 웹프로그램 / 기존 서비스 개선 / 아직 모르겠음 |
| 문의 내용 | 필수, 제작 목적·불편한 점을 자유롭게 설명 |
| 현재·참고 사이트 주소 | 선택, 안전한 URL 처리 |
| 희망 일정 | 선택, 일정 미정 허용 |
| 예산 정보 | 기본적으로 선택이며 필요 없다면 생략, 임의 가격 구간 금지 |

전화번호, 첨부파일, 회원가입은 기본 필수로 추가하지 않는다. 파일 업로드는 별도 요구가 없으면 구현하지 않는다. 문의 유형은 진입 페이지에 따라 미리 선택하되 수정 가능하게 한다.

## 개인정보 안내

기존 승인된 정책과 실제 수집·보관·전송 방식을 확인하고 필요한 안내와 동의를 적용한다. 동의를 미리 선택하지 않는다. 수집 목적·항목·보유 기간을 실제 운영과 다르게 임의로 작성하지 않는다. 미확정 사항은 운영자 확인 항목으로 기록하며, 외부 수집 서비스 도입을 임의로 하지 않는다.

## 실제 접수

1. 기존 모듈의 저장·수신·알림 기능과 접근 권한부터 확인한다.
2. 사용할 수 있는 기존 서버 경로가 있으면 재사용한다.
3. 없으면 G7 확장 구조에서 구현한다. 템플릿에 비밀키나 직접 메일 자격증명을 넣지 않는다.
4. 고객 문의를 저장하는 구조라면 권한 있는 관리자가 확인할 수 있는 기존 관리 화면 또는 적절한 관리 경로가 있어야 한다.
5. 메일만 전송하는 구조라면 서버의 실제 전송 접수 성공을 확인한다. 전송 요청 성공과 최종 배달은 구분한다.
6. 저장 성공 뒤 알림만 실패하는 경우 고객에게 접수 실패라고 잘못 표시하지 않는다. 재시도와 운영자 오류 확인 방법을 마련한다.
7. 최종 상태에 맞는 응답을 보여준다. 접수 성공일 때만 ‘문의가 접수되었습니다’를 표시한다. 회신 시간을 임의로 약속하지 않는다.

## 실패와 보안

- 클라이언트와 서버 양쪽 검증, 최대 길이, 허용값 확인.
- 기존 G7의 CSRF·세션·권한 패턴 준수. 그누보드 5 함수를 추측해서 사용하지 않는다.
- 실제 환경에 맞는 요청 제한·허니팟 등 스팸 방어. 외부 CAPTCHA를 임의로 가입·추가하지 않는다.
- 중복 클릭 방지, 전송 중 상태, 타임아웃/실패 후 입력 보존과 재시도.
- 접수 저장·전송의 중복 발생 위험을 구조에 맞게 처리한다.
- 입력값의 출력 이스케이프, 메일 헤더 삽입 방지, 서버 오류 상세 비노출.
- 로그에는 비밀키·문의 전문·개인정보를 남기지 않는다. 운영에 필요한 비식별 상태만 남긴다.
- 이메일이나 고객 입력 링크를 그대로 HTML로 렌더링하지 않는다.

## 설정이 없을 때

기존 승인된 연락 경로가 있으면 사실에 맞게 표시한다. 없으면 가상의 이메일·카카오 링크·전화번호를 만들지 않는다. 구현 가능한 서버·UI와 로컬 테스트는 완료하고, 수신 주소/환경변수/정책 등 필요한 값을 배포 차단 항목으로 기록한다.

현재의 ‘준비 중 + 비활성 폼’을 최종 영업 화면으로 납품하지 않는다. 실제 접수 또는 검증된 연락 경로가 없으면 ‘운영 공개 준비 완료’로 보고하지 않는다.

## 검증

승인된 로컬 테스트 수신기나 목으로 성공·실패·중복·검증 오류를 테스트한다. 운영 관리자에게 테스트 문의나 메일을 보내는 행위는 사용자 승인 뒤 수행한다. 테스트 결과에는 로컬 검증인지 실제 외부 수신까지 확인했는지 명확히 쓴다.
